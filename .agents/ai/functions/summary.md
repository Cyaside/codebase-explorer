# Summary Function Guide

## Goal

Explain what the repository is for and how a developer should mentally frame it.

## Questions To Answer

- what does the project appear to do
- what kind of system is it
- what are the main entry points
- what are the main technologies
- what is the most practical first mental model

## Evidence To Inspect

Prioritize:
- README and docs
- entry points
- top-level module layout
- package manager and lock files
- framework config files
- main runtime files

## Output Shape

The summary should produce:
- one short project summary
- one short system-type statement
- one short onboarding note

## Good Summary Characteristics

- concrete
- repo-specific
- path-aware
- low on filler

## Do Not

- describe the project as if it were a generic template
- overclaim architecture certainty from shallow evidence
- ignore repo docs when they exist

## Done Condition

A new developer can read the summary and know what kind of project they just opened.
